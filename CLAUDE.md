# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

FPGA design (SystemVerilog / Verilog) for a Tang Nano 9K (Gowin GW1NR-9C, `GW1NR-LV9QN88PC6/I5`) that captures video from an OV7670 camera and renders it to a 4.3" LCD in real time, with on-the-fly vertical resizing to preserve aspect ratio. Frames are 640x480 RGB565 buffered in external PSRAM via a 3-frame circular buffer.

## Repository layout

- `src/` — synthesizable RTL. The Gowin IP cores (`gowin_rpll`, `gowin_sdpb`, `gowin_sdpb_dn`, `gowin_alu54`, `fifo_top`, `psram_memory_interface_hs_2ch`, `sdpb_1kx32`, `cam_settings_rom`) are generated by Gowin IDE — regenerate them through the IDE rather than hand-editing the `.v`/`.vo` outputs.
- `src/fsms/` — `FrameUploader.sv` (PSRAM → LCD) and `FrameDownloader.sv` (camera → PSRAM) state machines.
- `sim/` — Icarus Verilog testbenches plus models (`psram_model.sv`, `i2c_slave_model.sv`).
- `FPGADesignElements/` — git submodule (laforest/FPGADesignElements) for CDC/pipeline primitives. Clone with `--recurse-submodules`.
- `scripts/scaler_generator.py` — generates lookup tables for `PositionScaler_horz.sv` / `PositionScaler_vert.sv`.
- `physical/` — OpenSCAD + STL for the 3D-printed enclosure.
- `camera_ov7670.gprj` — Gowin IDE project file (authoritative list of enabled synthesis sources and constraint files).

## Build and test

**Bitstream build:** open `camera_ov7670.gprj` in Gowin IDE (≥ 1.9.9 Beta-4) and run synthesis/PnR there. Upload via Gowin Programmer. There is no CLI build target for the bitstream — `src/CMakeLists.txt` only defines a `cam_synthesize` custom target that invokes `GowinSynthesis` on a subset of sources (I2C + camera config) and is not a full place-and-route flow.

**Simulation tests** are CMake-driven and run on both Windows and POSIX hosts. `sim/CMakeLists.txt` picks the per-test wrapper based on `WIN32` — `run_simulator.bat.in` on Windows, `run_simulator.sh.in` on Linux/macOS — and on non-Windows invokes the generated wrapper through `sh` (so it does not need an executable bit, keeping the project compatible with `cmake_minimum_required(3.8)`).

Configure and run:

```
# Linux/macOS
cmake -D IVerilog_PATH=/usr/bin -D Gowin_PATH=/opt/gowin/IDE [-D DUMP_SIM_VARIABLES=ON] <build_dir>
# Windows
cmake -D IVerilog_PATH=<iverilog\bin> -D Gowin_PATH=<Gowin install root> [-D DUMP_SIM_VARIABLES=ON] <build_dir>
```

`Gowin_PATH` is required on every platform — CMake locates `simlib/gw1n/prim_tsim.v` and the `GowinSynthesis` binary under it, so you need a Linux Gowin EDA install (not just iverilog) to run tests on Linux. `DUMP_SIM_VARIABLES=ON` produces `dump.vcd` per test under `<build>/sim/tests/<test_name>/` for GtkWave. Log verbosity is `-D SimLogLevel=Fatal|Error|Info|Debug|None` (default `Info`), which sets `SVL_VERBOSE_*` in the generated `test_config.sv`.

To run a single test, build then invoke `ctest -R <test_name>_run -V` in the build dir, or build the per-test custom targets `<test_name>_BUILD` / `<test_name>_SIM`. The list of tests lives in the `TESTS_LIST` variable in `sim/CMakeLists.txt` — adding a new `.sv` testbench requires appending its base name there. When adding a new platform wrapper, keep `run_simulator.bat.in` and `run_simulator.sh.in` in sync; both consume `@VERILOG_SIM@` and `@TEST_OUTPUT_FILE@` and redirect output to `output.txt` in the per-test working directory.

The legacy `sim/run_test_baseline.bat` and `sim/run_test_video.bat` are standalone iverilog invocations with hard-coded paths (`c:\iverilog\bin`, `C:\Gowin\Gowin_V1.9.9Beta-4`) — they are not driven by CMake and may lag behind.

## Architecture

Three clock domains generated by the Gowin rPLL (`src/gowin_rpll/memory_rpll.v`):

- **27 MHz** — system / camera XCLK / I2C-side logic.
- **135 MHz** — PSRAM controller and HyperRAM interface.
- **67.5 MHz** — buffer/arbiter logic (half of memory clock).
- **13.5 MHz** — LCD pixel clock.

Crossings between these domains use the `CDC_*` and `Pulse_*`/`Pipeline_*` primitives from `FPGADesignElements/` — re-use those rather than rolling new synchronizers.

Data path:

1. `i2c_control_fsm` + `i2c_master*` push the register map from `ov7670_default.sv` (table defined via `ov7670_regs.vh`) over SCCB at power-on to configure the camera.
2. `cam_pixel_processor.sv` packs the OV7670 byte stream into RGB565 pixels and feeds the camera-side FIFO (`fifo_top/fifo_cam_data`).
3. `BufferController.sv` together with the `FrameDownloader`/`FrameUploader` FSMs implement the 3-frame circular buffer described in `README.md`: independent read/write pointers cycle frame1→frame2→frame3, with skip-frame on fast writer and repeat-frame on fast reader. The `arbiter.v` mediates PSRAM access between the two FSMs.
4. `psram_memory_interface_hs_2ch` is the Gowin HyperRAM PHY. In simulation it is replaced by `sim/psram_model.sv`.
5. `video_controller.sv` drives `lcd_controller.sv` using `VGA_timing.v`, pulling pixels back out of PSRAM through the upload path. `PositionScaler_horz.sv` / `PositionScaler_vert.sv` (currently only vertical scaling is functional — see README "Known issues") do the resize between 640x480 source and the LCD resolution; their coefficient ROMs are generated by `scripts/scaler_generator.py`.
6. `debug_pattern_generator.sv` / `debug_pattern_generator2.sv` provide synthetic frames that bypass the camera path for bring-up and the `debug_pattern_*` simulations.

Constraints live in `src/camera_ov7670.cst` (pin assignments) and `src/camera_control.sdc` (timing).

## Conventions to preserve

- Synthesizable RTL targets SystemVerilog 2012 (`iverilog -g2012`). Match the existing mix of `.v` (older I2C / arbiter / Gowin IP) and `.sv` (newer controllers and FSMs); don't rewrite working `.v` modules into `.sv` for cosmetic reasons.
- When adding a new top-level synthesizable module, register it in **both** `camera_ov7670.gprj` (so Gowin IDE picks it up) and the relevant CMake source list (`VIDEO_BUFFER_TEST_SOURCES` in `sim/CMakeLists.txt`, or `SYNT_SOURCES` in `src/CMakeLists.txt` if it belongs to the standalone synthesis target).
- New testbenches must `` `include "test_config.sv" `` (generated by CMake) so they inherit the `DEFAULT_LOG_LEVEL` and optional `ENABLE_DUMPVARS` macros, and should use `svlogger.sv` for output rather than raw `$display`.
